# GitHub growth plan

10,000 stars is a long-term goal, not a measurable quality benchmark or a guaranteed outcome.

The strongest distribution hypothesis is a product developers can test without opening an account. The offline demo should show how a local check catches and verifies a bug, while its output explicitly says the planning decisions are scripted. A second public demo should use a real provider once benchmark data exists.

## Before launch

Ship a two-minute reproducible demo, clear install instructions, a real screenshot made from a running Studio instance, CI badges earned by actual builds, and a narrow issue template for verification bugs. Test Windows and macOS installations rather than relying on a configured workflow file. Eliminate false PASS cases before adding features.

## First month

Recruit 10 to 20 volunteer developers who already use coding agents. Ask them to run the hook on a normal project and report a confusing repeated diagnostic or incorrect cache decision. Log reported problems publicly with minimal reproducible fixtures. Track successful installs and first useful checks, not just stars.

## Days 30 to 90

Run matched before/after coding tasks with the same model, project, task, tool permissions and temperature when possible. Measure code correctness, number of model turns, actual input/output token counts when supported, user interventions, and elapsed time. Publish negative results as well as positive ones. Improve repeated-failure identity before chasing agent feature breadth.

## Days 90 to 180

Create a compatibility guide for Claude Code, Codex, OpenCode and other providers based only on tested versions. Add a small integration gallery. Develop a plugin test harness and a safe workflow-sharing process. Build contributor onboarding and maintain releases on a predictable cadence.

## Days 180 to 365

If retention and benchmarks are strong, submit a factual Show HN post and technical walkthroughs in relevant developer communities. Avoid coordinated voting or artificial stars. Publish a roadmap driven by reported usage. If adoption is weak, re-examine whether the main feature solves a frequent enough problem instead of adding more feature flags.

## Measures worth recording

Time-to-first-useful-check, installation failure rate, weekly active local repositories (only if users opt in to shared telemetry), false diagnostic suppression reports, true diagnostic savings, repeat users, public issues closed, outside contributors, benchmark pass rate and monthly stars.

Telemetry collection is off by default. No download/stars graph should be fabricated.
